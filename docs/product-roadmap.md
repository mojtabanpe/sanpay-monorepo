# رودمپ تکمیل سن‌پی

## هدف و دامنه

این رودمپ نیازهای اپ کارمند، پنل فروشگاه، پنل مدیریت و سرویس تسویه را به یک برنامهٔ اجرایی قابل تحویل تبدیل می‌کند. مبنای آن وضعیت فعلی Nx workspace شامل `app`، `store`، `dashboard` و `api` است.

## وضعیت فعلی و شکاف‌ها

| موضوع | وضعیت فعلی | اقدام لازم |
| --- | --- | --- |

## فاز صفر — تثبیت و خط مبنا (۲ تا ۳ روز)

1. ثبت سناریوی دقیق خرابی ورود پنل فروشگاه در محیط staging و مرور لاگ API/مرورگر.
2. افزودن correlation id و audit log برای login، payment، OTP و settlement بدون ثبت رمز یا OTP خام.
3. ساخت smoke test برای ورود هر سه سطح: کارمند، فروشگاه و مدیر.
4. مستندسازی timezone به‌صورت `Asia/Tehran` و قرارداد تاریخ API به‌صورت Gregorian ISO.

**خروجی قابل پذیرش:** خطای ورود قابل بازتولید و اندازه‌گیری است؛ تست ورود موفق، رمز اشتباه، فروشگاه غیرفعال و توکن منقضی پاس می‌شود.

## فاز یک — اصلاح UX اپ و اطلاعات فروشگاه (اسپرینت ۱، یک هفته)

### اپ کارمند

- همهٔ ورودی‌های تاریخ تولد با تقویم شمسی نمایش داده شوند و فقط هنگام ارسال به API به میلادی ISO تبدیل شوند.
- پس از navigation تازه، صفحه به بالا برود؛ در browser back موقعیت قبلی حفظ شود. shellهایی که اسکرول داخلی دارند نیز پوشش داده شوند.
- دکمهٔ بازگشت در صفحات داخلی اضافه شود؛ اگر history داخلی وجود نداشت به صفحهٔ خانه برگردد.
- هنگام خروج از صفحهٔ QR، تغییر مرحله، browser back و background شدن اپ، تمام trackهای MediaStream متوقف شوند.

### اطلاعات و کارت فروشگاه

- فیلدهای `phone` و `address` برای فروشگاه اجباری شوند.
- فیلدهای `latitude`، `longitude` و `logoUrl` به فروشگاه اضافه شوند.
- لوگو با محدودیت نوع/حجم، preview و تصویر fallback دریافت شود.
- کارت فروشگاه در صفحهٔ خانه و صفحهٔ فروشگاه‌ها شامل لوگو، آدرس، تلفن، «خرید» و «مسیریابی» باشد.
- مسیریابی با deep link نقشه و fallback وب باز شود؛ مختصات بر متن آدرس اولویت داشته باشد.

**معیار پذیرش:** اطلاعات هر فروشگاه در مدیریت قابل ثبت/ویرایش است، هر دو نوع کارت یک رفتار دارند، و دوربین حداکثر یک ثانیه بعد از خروج آزاد می‌شود.

## فاز دو — گزارش فروشگاه و پرداخت حضوری با OTP (اسپرینت ۲، ۱ تا ۲ هفته)

### گزارش فروشگاه

- فهرست تراکنش‌ها با بازهٔ شمسی، مبلغ، شماره رسید و وضعیت تسویه.
- وضعیت‌ها برای فروشگاه: «در انتظار ارسال»، «در حال پردازش»، «واریزشده» و «ناموفق».
- جزئیات واریز شامل کد پیگیری، زمان واریز و لینک رسید تومان؛ خطای داخلی/حساس نمایش داده نشود.
- جمع مبالغ و تعداد نتایج توسط سرور محاسبه شود، نه فقط صفحهٔ جاری.

### پرداخت فروشگاه‌محور

جریان پیشنهادی:

1. فروشگاه کد ملی، موبایل و مبلغ را وارد می‌کند.
2. API تطابق کارمند، فعال‌بودن استخدام، اعتبار و دسترسی فروشگاه را بررسی می‌کند.
3. یک `MerchantPaymentIntent` با OTP هش‌شده، زمان انقضا و تعداد تلاش ساخته و SMS ارسال می‌شود.
4. مشتری OTP را به فروشنده اعلام می‌کند و فروشنده ثبت می‌کند.
5. API در یک تراکنش دیتابیس OTP و موجودی را بررسی و پرداخت را فقط یک‌بار نهایی می‌کند.

کنترل‌های ضروری: انقضای ۲ دقیقه‌ای، محدودیت ارسال و تلاش، idempotency key، قفل/کنترل هم‌زمانی موجودی، ثبت audit، عدم افشای وجود کاربر قبل از تطابق کد ملی و موبایل.

**معیار پذیرش:** ارسال مجدد یا submit هم‌زمان باعث برداشت دوباره نمی‌شود؛ OTP منقضی/اشتباه و اعتبار ناکافی پیام کنترل‌شده دارد؛ رسید در اپ کارمند و پنل فروشگاه دیده می‌شود.

## فاز سه — تسویه، retry دستی و تقویم ذی‌نفعان (اسپرینت ۳، ۱ تا ۲ هفته)

### تقویم ساعت ۰۲:۰۰ تهران

| ذی‌نفع | روزهای اجرا |
| --- | --- |
| فروشگاه‌ها | هر شب |
| هتل‌یار | یکشنبه |
| اقامت۲۴ | یکشنبه و سه‌شنبه |

- انتخاب اقلام هر ذی‌نفع قبل از ساخت batch فیلتر شود؛ اجرای تکراری cron همچنان idempotent بماند.
- رزروها و پرداخت‌های خارج از روز مجاز برای اجرای بعدی باز بمانند.
- تست timezone و تغییر روز در ساعت ۰۰:۰۰ تا ۰۳:۰۰ تهران اضافه شود.

### retry دستی

- آیتم نهایی `FAILED` خودکار دوباره ارسال نشود.
- مدیر از صفحهٔ تسویه، پس از مشاهدهٔ علت، «تلاش مجدد» را اجرا کند.
- retry با tracker جدید و ارتباط با آیتم قبلی ثبت شود؛ تاریخچه حذف یا overwrite نشود.
- عملیات role-protected، audit شده و دارای confirmation باشد.

**معیار پذیرش:** شکست نهایی تا اقدام مدیر ثابت می‌ماند؛ retry دوباره‌برداشت ایجاد نمی‌کند؛ پرداخت فروشگاه وضعیت واریز صحیح را می‌بیند.

## فاز چهار — گزارش مدیریت و خروجی‌ها (اسپرینت ۴، یک هفته)

- گزارش پرداخت با فیلتر فروشگاه، شرکت، کارمند، وضعیت تسویه، بازهٔ شمسی، مبلغ و شماره رسید.
- خروجی Excel از کل نتایج فیلترشده در سمت سرور، نه فقط صفحهٔ فعلی؛ تاریخ‌ها، مبالغ و شناسه‌ها ستون‌های typed داشته باشند.
- نمای چاپ با عنوان گزارش، فیلترهای اعمال‌شده، زمان تولید، جمع کل، شماره صفحه و حذف کنترل‌های UI.
- محدودیت اندازه/صف‌بندی برای گزارش‌های بزرگ و ثبت audit دانلود.

**معیار پذیرش:** مجموع Excel، چاپ و UI برای یک فیلتر یکسان برابر است و نقش VIEWER فقط امکان مشاهده/خروجی مجاز دارد.

## فاز پنج — پشتیبانی کارمند چندشرکتی (اسپرینت ۵، ۱ تا ۲ هفته)

### تغییر مدل

- هر استخدام به‌صورت رکورد مستقل با `companyId`، کد پرسنلی، کارت‌ها/کیف‌پول‌ها و وضعیت خودش نگهداری شود.
- کد ملی بتواند در شرکت‌های مختلف تکرار شود، ولی ترکیب شرکت و کد ملی یکتا باشد.
- موبایل برای هر استخدام اجباری و در کل سامانه یکتا باشد؛ اگر همان موبایل برای شرکت دوم استفاده شد پاسخ duplicate برگردد.
- کد پرسنلی حداقل در محدودهٔ شرکت یکتا باشد.

برای کاهش ریسک، مدل پیشنهادی بلندمدت `Person + Employment + AuthIdentity` است؛ اگر سرعت مهاجرت اولویت دارد، می‌توان ابتدا Employeeهای مستقل با uniqueهای مرکب ساخت و سپس هویت شخص را جدا کرد.

### تجربهٔ کاربر

- ورود با کد ملی + موبایل، استخدام صحیح را بدون ابهام انتخاب کند.
- کارت‌ها، کیف‌پول‌ها، تراکنش‌ها و پروفایل هر شرکت کاملاً جدا باشند.
- ورود اطلاعات و import اکسل خطای «این موبایل قبلاً استفاده شده» را در سطح ردیف گزارش کند.

**معیار پذیرش:** یک کد ملی با دو موبایل در دو شرکت قابل ثبت است؛ همان موبایل در شرکت دوم رد می‌شود؛ داده و اعتبار دو استخدام هیچ‌وقت با هم مخلوط نمی‌شوند.

## ترتیب انتشار پیشنهادی

1. **Release 1:** رفع ورود + UXهای بحرانی + اطلاعات/کارت فروشگاه.
2. **Release 2:** گزارش فروشگاه + پرداخت OTP.
3. **Release 3:** وضعیت تسویه + retry دستی + تقویم‌های جدا.
4. **Release 4:** Excel/چاپ مدیریت.
5. **Release 5:** مهاجرت چندشرکتی، ابتدا staging و سپس rollout کنترل‌شده.

برآورد کل برای یک تیم متشکل از یک بک‌اند، یک فرانت‌اند و QA حدود **۶ تا ۸ هفته** است. با یک توسعه‌دهندهٔ تمام‌وقت، برآورد واقع‌بینانه **۱۰ تا ۱۲ هفته** است. این برآورد پس از فاز صفر و روشن‌شدن جزئیات سرویس SMS، ذخیره‌سازی لوگو و قرارداد تومان بازبینی می‌شود.

## Definition of Done مشترک

- migration با rollback plan و دادهٔ staging تست شده باشد.
- تست واحد برای قواعد مالی و تست integration برای OTP/تسویه وجود داشته باشد.
- تست end-to-end مسیرهای بحرانی موبایل و دسکتاپ پاس شود.
- هیچ OTP، توکن، کد ملی کامل یا پاسخ حساس سرویس تومان در log ثبت نشود.
- مانیتورینگ نرخ خطای login، SMS، payment و settlement و alert عملیاتی فعال باشد.
- هر قابلیت دارای معیار پذیرش، مجوز نقش‌ها و مستندات پشتیبانی باشد.
