# مهاجرت داده‌های آزمایشی تومن به محیط عملیاتی

این دستورها از ریشهٔ ریپوی سرور و با `compose.production.yml` و `.env.production` اجرا می‌شوند. اسکریپت‌ها خودشان تنظیمات تومن را تغییر نمی‌دهند و هیچ پرداخت/بازگشت وجه/لغو رزرو نزد ارائه‌دهنده انجام نمی‌دهند. حذف فقط در دیتابیس سن‌پی است.

## پاک‌سازی یک‌بارهٔ داده‌های آزمایشی

این رویه برای دیتابیسی است که **تمام تراکنش‌هایش آزمایشی هستند**؛ رکوردهای قدیمی برچسب staging/production ندارند و تشخیص محیط هر رکورد ممکن نیست. فیلتر درگاه یا تاریخ وجود ندارد. آدرس‌های تومن در تصمیم حذف نقشی ندارند و لازم نیست آن‌ها را به staging برگردانی؛ تأیید صریح `--confirm-all-data-is-test` ملاک اجرای حذف است. این دستور هیچ درخواستی به تومن ارسال نمی‌کند.

1. نسخهٔ حاوی این تغییرات را روی سرور دریافت کن؛ فایل‌های اسکریپت باید در `deploy/` باشند. اجرای حذف به درحال‌اجرا بودن API یا مقدار آدرس‌های تومن وابسته نیست؛ دیتابیس PostgreSQL باید در دسترس باشد.
2. پیش‌نمایش بدون تغییر داده:

```bash
bash deploy/reset-staging-finance.sh
```

3. حذف داده‌های آزمایشی و اصلاح مانده‌ها:

```bash
bash deploy/reset-staging-finance.sh --apply --confirm-all-data-is-test
```

این دستور API و jobهای داخل آن را متوقف می‌کند، دیپلوی خودکار را با `.deploy/finance-maintenance` متوقف نگه می‌دارد، بکاپ کامل و بررسی‌شدهٔ دیتابیس در `.deploy/backups/` می‌سازد، سپس حذف را در یک تراکنش انجام می‌دهد. در صورت خطای SQL، حذف و اصلاح مانده‌ها rollback می‌شوند. بکاپ، مسیر فایل و پیام موفقیت را نگه دار. به `flock` روی سرور لینوکسی نیاز است؛ همان ابزاری که دیپلوی دوره‌ای استفاده می‌کند.

موارد حذف‌شده: خریدهای فروشگاهی، تراکنش‌های دفتر مالی (شامل اصلاحات آزمایشی)، درخواست‌های پرداخت، تلاش‌های تمام درگاه‌ها، بازگشت وجه، بررسی‌های دستی، دسته‌ها و اقلام تسویه، درخواست‌های خرید با QR/OTP، رزروهای هتل و پرواز، قیمت‌های پرواز و webhookهای رزرو. حذف رزروها مانع پردازش/تسویهٔ مجدد رزرو آزمایشی در محیط عملیاتی می‌شود؛ این کار رزرو بیرونی را لغو نمی‌کند.

کارمندها، شرکت‌ها، فروشگاه‌ها، مدیرها، رمزها، تعریف کیف پول و تخصیص اعتبار حفظ می‌شوند. مصرف (`spent`) همهٔ تخصیص‌ها صفر می‌شود؛ سقف **فعلیِ تخصیص‌یافته**ٔ اعتبار رفاهی، تاریخ انقضا و وضعیت فعال حفظ می‌شود. سقف و مصرف کیف پول شخصی هر دو صفر می‌شوند تا پول کارت آزمایشی اعتبار واقعی نسازد. اصلاحات قبلی سقف اعتبار به سقف اولیه برنمی‌گردند.

API بعد از موفقیت یا خطا خودکار روشن نمی‌شود. اسکریپت بعد از موفقیت فایل `.deploy/staging-finance-reset.completed` می‌سازد و اجرای دوبارهٔ حذف را رد می‌کند. اگر بکاپ/SQL خطا داد، ابتدا خطا را رفع کن؛ فایل maintenance را بی‌بررسی حذف نکن.

## تنظیم و راه‌اندازی محیط عملیاتی

در `.env.production` مقادیر زیر را با اعتبارنامه‌های Production تنظیم کن. بانکداری شرکتی و IPG تنظیمات مستقل دارند؛ `live` به‌تنهایی آدرس staging را تغییر نمی‌دهد.

```dotenv
TOMAN_MODE=live
TOMAN_AUTH_URL=https://accounts.qbitpay.org/oauth2/token/
TOMAN_API_URL=https://dbank.toman.ir/api/v1
TOMAN_SETTLEMENTS_ENABLED=false

TOMAN_IPG_MODE=live
TOMAN_IPG_URL=https://ipg.toman.ir
TOMAN_IPG_AUTH_URL=https://accounts.qbitpay.org/oauth2/token/
UPG_GATEWAYS=toman
# UPG_PUBLIC_URL باید دامنهٔ عمومی HTTPS اپ باشد؛ callback: /api/upg/callback/toman
```

چهار مقدار `TOMAN_USERNAME/PASSWORD/CLIENT_ID/CLIENT_SECRET` برای بانکداری شرکتی‌اند. IPG می‌تواند چهار مقدار مستقل با پیشوند `TOMAN_IPG_` داشته باشد؛ اگر کامل نباشند، برنامه از اعتبارنامه‌های بانکداری شرکتی استفاده می‌کند. حساب و scopeهای هر سرویس باید از طرف تومن فعال باشند. پس از تست موفق تسویهٔ دستی و فعال بودن دسترسی/IP مجاز، برای اجرای زمان‌بندی‌شده `TOMAN_SETTLEMENTS_ENABLED=true` بگذار و API را recreate کن.

پس از بررسی تنظیمات، maintenance را بردار و نسخهٔ جدید را دیپلوی کن:

```bash
rm .deploy/finance-maintenance
bash deploy/deploy.sh
```

`restart` به‌تنهایی env جدید را اعمال نمی‌کند؛ deploy سرویس را با env جدید می‌سازد. لاگ‌های شروع `configuration.corporate` و `configuration.ipg` باید آدرس Production، حالت live و وضعیت مورد انتظارِ enabled را نشان دهند. برای تست پرداخت و تسویه از مبلغ کوچک و ذی‌نفع تأییدشده استفاده کن؛ در محیط Production این عملیات واقعی‌اند.

## لاگ پایدار و بستهٔ عیب‌یابی

Compose مسیر `TOMAN_LOG_DIR=/app/data/toman-logs` را به `.deploy/toman-logs` روی میزبان متصل می‌کند. هر روز UTC یک فایل `toman-YYYY-MM-DD.jsonl` ساخته می‌شود و با دیپلوی/حذف کانتینر باقی می‌ماند. اجرای خارج Compose باید `TOMAN_LOG_DIR` را به یک مسیر پایدار و قابل‌نوشتن تنظیم کند. فایل‌ها دسترسی ۶۰۰ و پوشهٔ ساخته‌شده توسط برنامه دسترسی ۷۰۰ دارند. لاگ‌ها خودکار حذف نمی‌شوند؛ نگهداری/آرشیو فضای دیسک را مطابق سیاست سرور انجام بده. خطای نوشتن با `log.write_failed` روی stdout ثبت می‌شود و عملیات مالی را تکرار نمی‌کند.

برای گزارش مشکل، این دستور را اجرا کن و فایل `.tar.gz` خروجی را بفرست:

```bash
bash deploy/collect-toman-diagnostics.sh
```

اگر شناسهٔ پرداخت/intent/tracker/batch/فروشگاه را داری:

```bash
bash deploy/collect-toman-diagnostics.sh PAYMENT_OR_TRACKER_OR_BATCH_ID
```

این دستور فقط خواندنی است: فایل‌های لاگ هفت روز اخیر، تنظیمات مجاز و غیرمحرمانهٔ API و snapshot وضعیت دیتابیس را در `.deploy/diagnostics/` بسته‌بندی می‌کند؛ هیچ API مالی تومن را صدا نمی‌زند. snapshot حداکثر ۲۰۰۰ رکورد در هر بخش دارد؛ برای رخداد قدیمی‌تر یا دیتابیس شلوغ از شناسه استفاده کن. لاگ‌های قدیمی‌تر از هفت روز را جداگانه از مسیر ذخیره‌شده بردار. بسته شامل شناسه‌ها و مبالغ عملیاتی است، اما رمز، توکن، شماره کارت، شبا، موبایل، بدنهٔ خام callback و پاسخ خام ارائه‌دهنده در آن قرار نمی‌گیرد. فایل `.env.production` یا بکاپ کامل را برای عیب‌یابی نفرست.

کلیدهای پیگیری: `paymentId`، `intentId`، `trackerId`، `batchId`، `itemId`، `refundId`، `traceId` و `requestId`. `traceId` اجرای یک جریان و `requestId` یک درخواست HTTP با retry آن را مشخص می‌کند؛ شناسه‌های مالی مراحل جداگانه/cron را به هم وصل می‌کنند. زمان‌ها UTC هستند؛ زمان‌بندی تسویه همچنان ساعت ۰۲:۰۰ تهران است.

رویدادهای اصلی:

| رویداد                                                                               | کاربرد                                                                         |
| ------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------ |
| `configuration.*`                                                                    | محیط، فعال‌بودن سرویس و کامل‌بودن credential بدون مقدار آن                     |
| `settlement.schedule` / `settlement.poll_schedule`                                   | آیا job اجرا شد و enabled بود؟                                                 |
| `settlement.eligibility` / `settlement.ineligible` / `settlement.skipped`            | نبود خرید واجد شرایط، شبای نامعتبر، اجرای تکراری                               |
| `oauth.*`                                                                            | نبود تنظیمات، scope نامعتبر، شکست/موفقیت توکن و استفاده از کش                  |
| `http.*`                                                                             | URL مقصد، scope، status، زمان پاسخ، کد خطا، retry احراز هویت و کد شبکه/timeout |
| `payment.create.*` / `payment.redirect_ready`                                        | ساخت درگاه و ذخیرهٔ شناسه/آمادگی redirect                                      |
| `payment.callback_*`                                                                 | رسیدن callback و تطبیق شناسه‌ها                                                |
| `ipg.verify_fallback` / `payment.verification_result`                                | verify و استعلام جایگزین، تطبیق مبلغ                                           |
| `payment.topup_committed` / `payment.capture_failed` / `payment.completed`           | ورود پول به کیف پول، کسر اعتبار و تکمیل خرید                                   |
| `payment.fulfillment_failed` / `payment.unknown`                                     | شکست نهایی‌سازی یا نیاز به بررسی دستی                                          |
| `payment.reconcile*` / `payment.inquiry_*`                                           | پیگیری پرداخت بدون callback                                                    |
| `settlement.submit.*` / `settlement.commit_started` / `settlement.transfer_observed` | ساخت batch، افزودن اقلام، commit و وضعیت انتقال                                |
| `refund.*`                                                                           | ثبت و پیگیری بازگشت وجه                                                        |

پسوند `finished` یعنی اجرای آن متد تمام شد؛ موفقیت مالی را باید از `status`، رویداد `payment.completed` یا وضعیت نهایی دیتابیس تأیید کرد. برای تسویه فقط وضعیت انتقال `6` موفق است. خطاهای DNS/اتصال/TLS معمولاً در `causeCode`، timeout در `errorName`، خطاهای Prisma در `errorCode` و خطاهای تومن در `httpStatus` و `codes` دیده می‌شوند. اگر ارائه‌دهنده دلیل ندهد یا callback اصلاً نرسد، لاگ محل توقف و آخرین وضعیت معلوم را نشان می‌دهد؛ علت داخلی بانک ممکن است به پیگیری با تومن و شناسهٔ درخواست نیاز داشته باشد.
