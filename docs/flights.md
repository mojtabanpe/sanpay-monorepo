## رزرو و اعتبار

1. `Search` پروازهای جفت‌شده را می‌گیرد؛ `Available` مرحله بعد Search نیست.
2. پیش‌فاکتور پنج‌دقیقه‌ای در دیتابیس و متعلق به کارمند ذخیره می‌شود. قیمت ارسالی مرورگر پذیرفته نمی‌شود.
3. هنگام پرداخت، پیش‌فاکتور پنج‌دقیقه‌ای و مالکیت، فعال‌بودن، انقضا، نوع کیف پول و مانده دوباره بررسی می‌شوند. شرط روی مانده قبلی جلوی برداشت هم‌زمان بیش از سقف را می‌گیرد؛ `quoteId` یکتا مانع تکرار تماس صدور است. Search دوباره اجرا نمی‌شود، چون محیط تست در هر جست‌وجو کلیدهای متفاوتی تولید می‌کند.
4. `Create` با همان کلیدهای پیش‌فاکتور ظرفیت و قیمت نهایی را بررسی و ظرفیت را نگه می‌دارد. فقط وضعیت `approved` و مبلغ `total_guest_price` مطابق پیش‌فاکتور اجازه `Book` می‌دهد. اختلاف یا نبود مبلغ در رزرو نگه‌داشته‌شده باعث برگشت اعتبار می‌شود و صدور انجام نمی‌شود؛ نگه‌داشت تأمین‌کننده منقضی خواهد شد.
5. `booked` قطعی، `booking` درحال‌پردازش و `rejected` ناموفق است (نمونه‌های Postman). رد قطعی یک‌بار اعتبار را با تراکنش `REFUND` برمی‌گرداند. شماره بلیت و PNR از پاسخ تأمین‌کننده ذخیره می‌شوند.
6. خطای شبکه اثبات رد رزرو نیست. هیچ درخواست نوشتنی خودکار تکرار نمی‌شود و اعتبار در رکورد قابل پیگیری باقی می‌ماند. بک‌اند هر ده ثانیه رزروهای باز دارای کد تأیید در ۲۴ ساعت اول را استعلام می‌کند. مرورگر هم وضعیت را هر ده ثانیه تازه می‌کند.

## موارد نیازمند پیگیری عملیاتی

`REVIEW` یعنی نتیجه نامشخص؛ موفقیت یا استرداد فرض نمی‌شود. رکورد بدون `confirmationCode` (مثلاً قطع ارتباط هنگام Create) و رکورد باز قدیمی‌تر از ۲۴ ساعت باید با پشتیبانی تأمین‌کننده تطبیق داده شود. کد داخلی، زمان، مسیر، پیش‌فاکتور و تراکنش در دیتابیس حفظ می‌شوند. مسیر بازیابی خودکار برای پاسخ گم‌شده Create در قرارداد وجود ندارد.

کنسلی اختیاری پس از صدور و تسویه بانکی خودکار تأمین‌کننده در این تغییر اضافه نشده‌اند. پروازها به batch تسویه هتل متصل نشده‌اند، چون نحوه شارژ/تسویه اعتبار وب‌سرویس پرواز باید جداگانه با تأمین‌کننده مشخص شود.

## بررسی

- `pnpm nx run api:test-flights`: مبلغ، تاریخ، مسافران، مالکیت، تکرار درخواست، تغییر قیمت، رد و خطای مبهم.
- `pnpm nx run api:test-flights-integration`: فقط PostgreSQL محلی؛ داده‌های مستقل موقت می‌سازد و پاک می‌کند. برداشت هم‌زمان، یکتایی رزرو و استرداد را بررسی می‌کند؛ تأمین‌کننده ساختگی است.
- `pnpm nx run-many -t build -p api app`
- `pnpm nx run-many -t lint -p api applet-tourism models`
- با اجرای اپ روی پورت ۶۲۰۰: `node apps/app/tests/flights-ui.cjs`. Playwright و مرورگر نصب‌شده لازم است؛ مسیر مرورگر را می‌توان با `PLAYWRIGHT_EXECUTABLE_PATH` تعیین کرد. تمام درخواست‌های API در این تست جایگزین می‌شوند؛ رزرو یا پرداخت واقعی انجام نمی‌شود.

اتصال محیط تست در ۲۰۲۶-۰۹-۲۴ با Client-Token تنها بررسی شد. `pnpm nx run api:check-eghamat24` فهرست شهرها، هتل‌های مشهد، جزئیات، موجودی و جست‌وجوی پرواز را از کلاینت‌های واقعی دریافت می‌کند. این فرمان فقط GET می‌زند و رزرو یا پرداخت ایجاد نمی‌کند.
